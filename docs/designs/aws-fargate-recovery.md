# Fargate 재실행과 태스크 이력

[Daily Brief AWS 전환 설계](daily-brief-aws.md)의 배치 복구 기본값에 대한 제안이다.

| 설정 | 초기 제안 |
| --- | --- |
| 재실행 간격 | 이전 태스크의 종료 확인 후 첫 재실행까지 5분, 두 번째 재실행까지 15분 |
| 실행 시간 제한 | 최초 제출 후 45분과 다음 08:00 KST 중 이른 시각에 중지를 요청 |
| 태스크 시도 이력 | 종료 시각 기준 30일 보존. 종료를 확인하지 못한 시도 및 종료 결과 기록이 보류된 시도는 정리 대상에서 제외 |

초기값은 동일 마감의 일시 오류를 빠르게 복구하면서 연속 재실행 사이에 대기 시간을 두기 위한 제안이다. 예약 발송 전에 대표 배치의 기동 시간과 처리 시간을 측정하고 45분 안에 정상적으로 완료할 여유가 있는지 확인한다.

## 실행 및 종료 규칙

- 최초 실행을 포함해 마감당 최대 세 번을 유지한다. 재실행을 제출하기 직전에 다음 08:00 KST 기한과 시도 한도를 확인한다. 정규 실행과 매시 15분 점검이 경합해도 DSQL 조건부 쓰기로 실행권을 얻은 시도만 시작한다.
- Step Functions 상태가 시간 초과되면 태스크 중지를 요청하고 ECS `DescribeTasks`에서 `lastStatus=STOPPED`를 확인한 후에만 재실행을 예약한다. 상태를 확인할 수 없으면 실행권을 유지하고 운영자에게 알린다. 다음 08:00 KST부터는 이전 마감의 중지 요청, 종료 확인과 결과 기록만 계속한다. [Step Functions ECS 통합](https://docs.aws.amazon.com/step-functions/latest/dg/connect-ecs.html) · [동기 작업 취소 동작](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html)
- 마감 ID, 시도 번호, 태스크 ARN, 시작·종료 시각, 종료 코드 및 분류를 시도 이력에 기록한다. 30일 정책은 종료된 태스크 시도 상세 행에 적용하며 마감의 마지막 완료 지점과 SES 수락 상태는 별도로 유지한다.
- 복구 시 마지막 완료 지점부터 진행한다. SES 수락 여부가 불명확한 발송은 보류 상태를 이어받는다. 시간 초과만으로 메일 재제출을 허용하지 않는다.

### 제출 응답 유실

`RunTask` 전에 마감 ID와 시도 번호에 고정된 `ClientToken`, 전체 요청 파라미터, 최초 제출 기준 시각, 워크플로 실행 ARN을 DSQL 시도 행에 기록한다. 실행권과 시도 행이 함께 커밋된 뒤 호출하며, 태스크 정의는 리비전까지 고정한다.

제출 결과가 불명확하고 태스크 ARN이 없으면 시도의 중지 요청 기한과 토큰 유효 기간 안에서만 저장된 토큰과 파라미터로 같은 클러스터에 다시 호출한다. 최초 호출이 ECS에 도달하지 않았으면 이 호출이 해당 시도의 첫 제출이 될 수 있다. ARN을 얻으면 기존 시도 행에 저장하고 시도 횟수는 유지한다. 기한이 지났거나 토큰 유효 기간 안임을 확인할 수 없으면 실행권을 유지하고 운영자에게 알린다. 새 토큰은 이전 시도의 종료 결과가 확정되고 재실행 조건을 충족할 때 다음 시도 번호에 발급한다. [ECS RunTask 멱등성](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ECS_Idempotency.html)

### 중단된 워크플로 점검

EventBridge Scheduler가 매시 15분 호출하는 Step Functions 점검 경로가 미시작 마감, 종료 결과가 기록되지 않은 시도, 재실행 대기 중인 마감을 확인한다. 원래 워크플로가 종료됐음이 확인되면 DSQL 조건부 갱신으로 점검 실행 하나가 후속 처리를 인수한다. 실행 상태 조회에 실패하면 기존 소유권을 유지한다.

태스크 ARN이 있으면 `DescribeTasks`로 상태를 확인하고, 아직 실행 중인 태스크가 중지 요청 기한을 지났으면 `StopTask`를 요청한다. ARN이 없으면 제출 응답 유실 절차를 따른다. 조회 오류나 `MISSING`이면 시도를 미종결 상태로 유지하고 운영자에게 알린다. `STOPPED`를 확인하면 종료 결과와 재실행 가능 시각을 DSQL에 기록한다. 재실행 대상이면 이 시각 이후에 같은 마감의 실행권을 다시 확보한 워크플로만 다음 시도를 시작한다. 워크플로가 대기 중 중단돼도 점검 경로가 저장된 시각을 기준으로 이어간다.

## AWS 실측 결과

2026-11-23에 서울 리전(`ap-northeast-2`)의 임시 ECS Fargate 태스크와 Step Functions Standard 워크플로에서 검증했다. 태스크는 BusyBox로 종료 동작을 재현했으며 Daily Brief 배치, DSQL, SES는 테스트에 연결하지 않았다.

| 검증 항목 | 관찰 결과 |
| --- | --- |
| 제출 응답 유실 모사 | 동일한 `ClientToken`과 요청 파라미터로 `RunTask`를 다시 호출하자 같은 태스크 ARN이 반환됐다. 같은 토큰으로 컨테이너 명령을 바꾸자 `ConflictException`이 반환됐다. |
| 시간 초과와 자동 중지 실패 | 워크플로 실행 역할에 `ecs:StopTask` 권한을 부여하지 않은 상태에서 `ecs:runTask.sync`가 `States.Timeout`으로 끝났다. 이후 조회한 태스크의 `lastStatus`는 `RUNNING`이었다. |
| 중지와 후속 실행 | 별도로 호출한 `StopTask`의 응답은 `desiredStatus=STOPPED`, `lastStatus=RUNNING`이었다. `DescribeTasks`에서 실제 `STOPPED`를 확인한 뒤 새 토큰으로 실행한 태스크는 종료 코드 `0`으로 끝났다. |
| 비정상 종료 | 컨테이너 종료 코드 `42`가 ECS에 기록됐고, Step Functions 실행은 `FAILED`와 `States.TaskFailed`를 기록했다. |
| 상태 조회 누락 | 존재하지 않는 태스크를 `DescribeTasks`로 조회하자 `tasks`는 비어 있었고 `failures[].reason`은 `MISSING`이었다. |

시간 초과, 중지 요청 응답, 조회 누락만 관찰된 시도는 실제 종료가 확인될 때까지 실행권을 유지한다. 후속 실행의 대기 시간은 `lastStatus=STOPPED`를 확인한 시점부터 적용한다.

검증 종료 시 실행 중인 테스트 태스크는 0개였다. 임시 스택 `dailybrief-pr2-probe`는 같은 날 15:54 KST에 `DELETE_COMPLETE`로 확인했다.

## 승인 전 통합 검증

- 실제 배치의 기동 시간과 전체 처리 시간을 측정해 45분 제한에 여유가 있는지 확인한다.
- 강제 시간 초과, 중지 실패, 상태 조회 오류·누락, 제출 응답 유실 시 DSQL의 실행권과 시도 횟수를 확인한다. 이전 태스크의 실제 종료 전에는 같은 마감의 새 태스크가 시작되지 않는지, 동일 제출을 복구할 때 시도 횟수가 늘지 않는지 확인한다.
- 제출 직후와 재실행 대기 중에 원래 워크플로를 중단하고 매시 점검이 각각 기존 시도와 저장된 재실행 시각을 이어받는지 확인한다. 점검이 중복 호출돼도 후속 처리를 한 실행만 인수하는지, 기한이 지난 제출을 다시 호출하지 않는지 검증한다.
- 5분·15분 자동 대기, 마감당 최대 3회, 다음 08:00 KST 경계와 한도·기한 도달 시 알림을 검증한다. 복구 시 저장된 완료 지점과 SES 수락 보류 상태가 이어지는지 확인한다.
- 30일 경계에서 만료된 종료 이력만 정리되고, 종료 미확인 시도 및 종료 결과 기록이 보류된 시도가 보존되는지 확인한다.
